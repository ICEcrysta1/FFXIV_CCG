# FFXIV CCG 命令行使用说明

所有命令都在仓库根目录执行，统一使用根目录 `.env`（由 `python-dotenv` 加载）和 `config/` 下的 YAML。
参数优先级固定为「命令行参数 > 根目录 `.env` > YAML / 程序默认值」，相对路径都相对项目根目录解析。

先激活项目虚拟环境（Python >= 3.12）：

```powershell
.\.venv\Scripts\Activate.ps1
```

项目只支持 NVIDIA CUDA 环境：训练、GRPO 后训练、ONNX 导出、模型分析和自回归回放都以 GPU 为唯一支持路径。

## 统一入口：ffxiv_ccg.ps1

日常使用只需要这一个入口，它用项目 `.venv` 调用下面对应的 Python 命令：

| 菜单 | `-Action` | 实际命令 |
|---|---|---|
| 1 训练（BC 预训练） | `train` | `python -m training.train` |
| 2 恢复训练 | `resume` | 仅支持恢复 BC checkpoint；无交互时使用 `-Checkpoint` 或配置默认 checkpoint。GRPO checkpoint 请通过菜单 3 作为权重热启动输入 |
| 3 GRPO 后训练 | `grpo` | 使用 `-Checkpoint` 或配置默认 checkpoint 执行 `python -m grpo --checkpoint <checkpoint>` |
| 4 ONNX 导出 | `export` | 使用 `-Checkpoint` 或配置默认 checkpoint 执行 `python -m scripts.onnx_export.workflow all --checkpoint <checkpoint>` |
| 5 模型分析图生成 | `analysis` | 使用 `-Checkpoint` 或配置默认 checkpoint 执行 `python -m scripts.model_analysis --checkpoint <checkpoint>` |
| 6 模型自回归回放 | `replay` | 使用 `-Checkpoint` 或配置默认 checkpoint 执行 `python -m scripts.autoregressive_replay --checkpoint <checkpoint>` |
| 7 FFLogs 数据下载 | `fflogs` | `python scripts/fflogs_scraper.py ...` |

```powershell
# 交互菜单：输入 1～7 执行对应工具，0 退出
.\ffxiv_ccg.ps1

# 无交互执行指定工具（`-Action` 使用 action 名称）
.\ffxiv_ccg.ps1 -Action train
.\ffxiv_ccg.ps1 -Action resume
.\ffxiv_ccg.ps1 -Action grpo
.\ffxiv_ccg.ps1 -Action export
.\ffxiv_ccg.ps1 -Action analysis
.\ffxiv_ccg.ps1 -Action replay

# 无交互时显式指定 checkpoint；不指定时回退到配置解析出的默认 checkpoint
.\ffxiv_ccg.ps1 -Action grpo -Checkpoint artifacts/checkpoints/black_mage/artzip_bc/best.pt
.\ffxiv_ccg.ps1 -Action export -Checkpoint artifacts/checkpoints/black_mage/artzip_bc_grpo/best.pt
```

菜单编号和 action 名称由 `scripts/ffxiv_ccg_menu.psm1` 统一解析；交互菜单选择 2～6 后都会先进入同一个 checkpoint 选择菜单。BC checkpoint 使用 `1`、`2`、`3` 编号，GRPO checkpoint 使用 `a1`、`a2`、`a3` 编号；2 只显示可恢复的 BC checkpoint，3～6 显示 BC 与 GRPO 的全部候选。非菜单 `-Action` 不读取 `Read-Host`：可通过 `-Checkpoint <路径>` 覆盖 checkpoint，省略时使用项目配置解析出的默认 checkpoint。菜单本身不保存业务参数：职业、模型变体、数据目录、精度、Provider 和门禁步数全部来自
`config/models/<job_tag>/<variant>/` 与根目录 `.env`。需要临时覆盖某个参数时，直接调用下文对应的 Python 命令。

## 1. FFLogs 数据下载

```powershell
# URL 方式：fight / source 从 URL 自动解析
python scripts/fflogs_scraper.py "https://www.fflogs.com/reports/<CODE>?fight=6&source=10"

# 参数方式
python scripts/fflogs_scraper.py single --report <CODE> --fight 6 --source 10

# 批量：按 encounter 排行榜下载高分报告
python scripts/fflogs_scraper.py batch -e 1079 --spec-name BlackMage --max-pages 3

# 列出 zone 下的 encounters / 列出全部 zones
python scripts/fflogs_scraper.py encounters -z 39
python scripts/fflogs_scraper.py encounters
```

需要在 `.env` 配置 `FFLOGS_V2_CLIENT_ID` 与 `FFLOGS_V2_CLIENT_SECRET`（FFLogs → 我的 → API）。
原始 JSON 默认写入 `data/`；转换脚本只读取模型 YAML 指定的 `raw_data_dir`，所以下载后要把文件放进
`data/human/job/<job>/raw/<副本>/`。

## 2. 训练（BC 预训练）

```powershell
# 使用 .env 与模型 YAML 的默认配置
python -m training.train

# 快速验证：按副本比例只取 3 个 raw JSON，转换失败时从同副本后备文件补位
python -m training.train --max-files 3

# 从 checkpoint 继续训练
python -m training.train --resume artifacts/checkpoints/black_mage/artzip_bc/epoch_009_ppg_569.63.pt
```

训练启动前会先把选中的 raw JSON 编译到 `data/human/job/<job>/.cache/`，不写回 `raw/`，也不产生中间训练 PT。
compiled cache 固定保存完整 history bank，`model.history_capacity` 只影响读取窗口，调整它不会触发 cache 重建。
参与训练与验证的 raw JSON 文件数由 `training.max_files` 控制，只接受正整数或 `null`（浮点、字符串等非整数取值直接报错，不做静默截断）。当前黑魔 `artzip` 配置为 `1280`，即省略 `--max-files` 时最多只会使用 1280 个文件；未配置该键或显式设为 `null` 时才不限制，使用 raw 目录下全部有效文件。一键脚本因此不需要额外参数即可限制数据量。该字段由 BC 预训练与 GRPO 后训练共用，GRPO 也按同一上限选择真实场景文件。
启动日志会打印实际参与的文件数与文件集合指纹，checkpoint 也会保存这两项：指纹按相对 raw 根目录的路径与文件字节数计算，既能区分不同副本目录下的同名文件，也能发现同名文件被替换后 cache 重建的情形。续训时用上限加指纹共同判断语料是否一致，避免 raw 目录增删文件后静默换训练集。

| 参数 | 默认值/来源 | 说明 |
|---|---|---|
| `--config` | `.env` 的 `FFXIV_JOB_TAG` + `FFXIV_MODEL_VARIANT` → `config/models/<job_tag>/<variant>/config.yaml` | 模型配置清单 |
| `--raw-data-dir` | 模型 YAML 的 `raw_data_dir` | raw JSON 目录 |
| `--output-dir` | 模型 YAML 的 `output_dir` | checkpoint 输出目录 |
| `--epochs` | `training.max_epochs`（当前 `8`） | 训练轮数 |
| `--batch-size` | `training.batch_size`（当前 `20`） | 每个 GPU batch 的样本数 |
| `--lr` | `training.learning_rate`（当前 `0.0001`） | AdamW 学习率 |
| `--max-files` | `training.max_files`（当前配置 `1280`；未配置或 `null` 时不限制） | 覆盖 YAML 的文件数上限；按副本目录比例分配，再按 `train_split` 划分训练集与验证集 |
| `--device` | `.env` 的 `TRAINING_DEVICE`（`cuda`） | 运行设备 |
| `--resume` | 不续训 | 从 checkpoint 恢复 optimizer、scheduler、best 指标和随机状态 |
| `--force-resume-data-mismatch` | 关闭 | 明确确认后允许 `checkpoint.run_config.max_files` 与当前配置不一致时续训；必须配合 `--resume` |

续训使用 `torch.load(weights_only=False)` 恢复完整 checkpoint 元数据，只应加载可信来源的 checkpoint。

### 默认 checkpoint

菜单 2～6 直接使用界面里选中的 checkpoint。省略 `-Checkpoint` 的非交互调用（`-Action grpo/export/analysis/replay`）回退到模型 YAML `output_dir` 下的 `best.pt`；如果在根目录 `.env` 里设置了 `TRAINING_MODEL_CHECKPOINT`（相对 `output_dir` 的文件名或绝对路径），该值会作为显式覆盖优先于 `best.pt`。回放另有 `AUTOREGRESSIVE_REPLAY_CHECKPOINT` 作为 pytorch 后端的显式覆盖。默认配置不再需要维护这几项，但保留它们是为了在不改动 YAML 的前提下临时切换默认 checkpoint。
ONNX 部署包路径不设 `.env` 开关：导出、parity、发布校验和 ONNX 回放都按所选 checkpoint 推导 `artifacts/exports/<job>/<run>`，只有 CLI 的 `--output-dir` / `--onnx-package` 能显式指定。旧版模板的 `AUTOREGRESSIVE_REPLAY_ONNX_PACKAGE` 不再被读取，设置它不会产生任何效果，也不会触发报错；这样菜单换成别的 BC/GRPO checkpoint 后不会再去写或检查旧模型的部署包目录。

### checkpoint 选择（菜单 2～6）

菜单 2～6 都不需要手写 checkpoint 路径：脚本通过项目自己的配置解析器读取根目录 `.env` 的 `FFXIV_JOB_TAG` 与 `FFXIV_MODEL_VARIANT`，定位 `config/models/<job_tag>/<variant>/config.yaml`，扫描 BC 的 `output_dir` 和同级 `<run>_grpo` 目录，再调用同一个 checkpoint 菜单。BC 的已完成 `max_epochs` 项在菜单 2 中跳过；菜单 2 不列出 GRPO checkpoint，菜单 3～6 仍可选择两类 checkpoint。目录里无法读取的 `.pt`（例如训练中断留下的截断文件）不会让菜单 2～6 一起失败：脚本会跳过它们，并在清单上方单独列出文件与原因。

### 恢复训练（菜单 2 / `-Action resume`）

交互菜单的菜单 2 仅支持选择可续训的 BC checkpoint；计划任务或 CI 使用 `-Action resume` 时不会等待输入，默认恢复配置解析出的 checkpoint，也可以通过 `-Checkpoint <路径>` 指定，选择 GRPO checkpoint 会被明确拒绝。需要从 GRPO checkpoint 启动新的 GRPO 后训练时，请使用菜单 3，将其作为权重热启动输入，不恢复旧运行状态。BC 恢复如需接受 `training.max_files` 不一致，追加 `-ForceResumeDataMismatch`；未追加时由训练入口直接拒绝，不会弹出交互确认。

菜单 2 的选择界面示例：

```text
当前 .env 配置：FFXIV_JOB_TAG=black_mage，FFXIV_MODEL_VARIANT=artzip
模型配置：config\models\black_mage\artzip\config.yaml
BC checkpoint 目录：artifacts/checkpoints/black_mage/artzip_bc
GRPO checkpoint 目录：artifacts/checkpoints/black_mage/artzip_bc_grpo
训练数据上限：1280（来自模型 YAML 的 training.max_files，BC 预训练与 GRPO 后训练共用）

   1. epoch_001_val_ppg_466.11.pt（BC，epoch 1，1000 个 raw 文件，目录 artzip_bc）
   2. epoch_002_val_ppg_455.85.pt（BC，epoch 2，1000 个 raw 文件，目录 artzip_bc）
   3. best.pt（BC，epoch 2，1000 个 raw 文件，目录 artzip_bc）
```

菜单 2 输入 BC 编号执行 `python -m training.train --resume <该文件>`；GRPO checkpoint 不支持连续恢复训练。菜单 3 的 `python -m grpo --checkpoint <该文件>` 仍表示从 BC/GRPO 权重开始新的 GRPO 后训练。BC 恢复按当前 YAML/命令行生效的 `training.max_files` 选择 raw JSON，并与 checkpoint 保存的 `run_config.max_files` 和实际文件集合指纹做一致性校验：只有上限相同并不足以证明语料一致，raw 目录增删文件后即使上限没变也会被识别为不同数据集。默认不一致或缺失指纹会弹出警告，直接回车或输入 `N` 取消，输入 `Y` 才会追加强制参数继续。
菜单内的指纹提示只是"预选"：脚本按首轮比例选中的文件预估集合，不编译 cache；真正训练入口会用实际编译结果（含失败时从同副本后备文件补位）判定。因此菜单没提示、训练入口仍报不一致（或相反）都是可能的，最终判定以训练入口为准。
清单长度不固定：训练未跑完时可能只有 BC 的 `epoch_*` 与 `best.pt`，GRPO 输出则可能有 `iteration_*`、`best.pt`、`latest.pt` 和 `final.pt`。每组按名称升序排列，`best.pt` 排在该组最后，每项显示的 epoch 或 iteration 来自 checkpoint 载荷本身。
BC 可恢复与否不看文件名：脚本读取载荷里的 `epoch`，用 `epoch >= training.max_epochs` 判定并跳过已完成 epoch；菜单 2 不列出 GRPO checkpoint。

## 3. GRPO 后训练

```powershell
# 使用当前职业配置和默认 BC checkpoint
python -m grpo

# 显式指定起始 checkpoint 和独立输出目录
python -m grpo --checkpoint artifacts/checkpoints/black_mage/artzip_bc/best.pt --output-dir artifacts/checkpoints/black_mage/artzip_bc_grpo
```

GRPO 不提供连续训练入口；`--checkpoint` 只用于以 BC/GRPO checkpoint 的模型权重启动新的 GRPO 后训练，不恢复旧运行的 optimizer、scheduler、RNG 或 iteration。

`--output-dir` 缺省时按来源 checkpoint 区分输出目录，都不会覆盖已有产物：

- 来源是 BC checkpoint（例如 `output_dir` 下的 `best.pt`）：输出到模型 YAML `training.output_dir` 同级的 `<run>_grpo/`。
- 来源是 GRPO checkpoint（例如 `<run>_grpo/iteration_010.pt`）：按同一基础目录派生 `<run>_grpo_hotstart/`，已存在时追加 `_001`、`_002` 后缀，避免重复热启动覆盖上一轮结果。
- 显式传入 `--output-dir` 时以该值为准。

每个场景先跑 1 条贪心基准，再生成
`group_size` 条采样轨迹；只有整轮 rollout 与奖励标注完成后才进入反向更新，更新后贪心 PPG 低于更新前超过
`greedy_guard_tolerance` 会被拒绝。命令行参数优先于 `grpo.yaml`。

| 参数 | 默认值/来源 | 说明 |
|---|---|---|
| `--config` | `.env` 的 `FFXIV_JOB_TAG` + `FFXIV_MODEL_VARIANT` | 模型配置清单 |
| `--checkpoint` | 菜单选择的 checkpoint；直接调用时默认为模型配置 `output_dir` 中的 `best.pt` | GRPO 初始 BC/GRPO checkpoint |
| `--raw-data-dir` | 模型 YAML 的 `raw_data_dir` | 真实训练场景目录 |
| `--max-files` | 模型 YAML 的 `training.max_files`（当前 `1280`；未配置或 `null` 时不限制） | 限制参与的真实场景文件数；与 BC 共用同一个 YAML 字段 |
| `--output-dir` | BC checkpoint：`<training.output_dir>_grpo`；GRPO checkpoint：`<training.output_dir>_grpo_hotstart[_NNN]` | GRPO 输出目录 |
| `--device` | `.env` 的 `TRAINING_DEVICE` | 运行设备 |
| `--precision` | 模型配置的 `precision` | 运行精度 |
| `--samples-per-scene` / `--group-size` | `grpo.group_size`（当前 `16`） | 每个场景的采样轨迹条数，不含贪心基准 |
| `--prompt-batch-size` | `grpo.prompt_batch_size`（当前 `8`） | 每轮处理的真实场景数 |
| `--iterations` | `grpo.max_iterations`（当前 `10`） | GRPO 外层更新轮数 |
| `--max-duration-seconds` | `grpo.max_duration_seconds`（当前 `1200`） | 每条轨迹的统一时间上限；`null` 表示跟随场景结束时间 |
| `--temperature` | `grpo.temperature`（当前 `1.3`） | 采样温度，必须大于 `0` |
| `--top-p` | `grpo.top_p`（当前 `1.0`） | 核采样累计概率阈值，范围 `(0, 1]` |
| `--inner-updates` | `grpo.inner_updates`（当前 `1`） | 每轮 rollout 后的策略更新次数 |
| `--minibatch-size` | `grpo.minibatch_size`（当前 `64`） | 每次策略更新使用的 rollout 决策数 |
| `--lr` | `grpo.learning_rate`（当前 `0.000001`） | GRPO AdamW 学习率 |
| `--warmup-steps` | `grpo.warmup_steps`（当前 `20`） | 学习率 warmup 更新步数 |
| `--clip-low` | `grpo.clip_low`（当前 `0.2`） | clipped surrogate ratio 下界 |
| `--clip-high` | `grpo.clip_high`（当前 `0.2`） | clipped surrogate ratio 上界 |
| `--kl-coefficient` | `grpo.kl_coefficient`（当前 `0.001`） | 行为策略与当前策略之间的 KL 惩罚权重 |
| `--greedy-guard-tolerance` | `grpo.greedy_guard_tolerance`（当前 `0.0`） | 更新后贪心 PPG 允许的最大下降量 |
| `--advantage-scale-floor-ratio` | `grpo.advantage_scale_floor_ratio`（当前 `0.1`） | 优势标准差的相对尺度下限 |
| `--advantage-clip` | `grpo.advantage_clip`（当前 `5.0`） | 优势的对称裁剪上限 |

## 4. ONNX 导出与发布门禁

```powershell
# 只导出整图并完成导出期验证（不登记发布状态）
python -m scripts.onnx_export

# 完整发布流程：环境检查 → 导出 → 空 scene parity → 真实 scene parity → 发布校验
python -m scripts.onnx_export.workflow all

# 只执行其中一步
python -m scripts.onnx_export.workflow empty-parity
python -m scripts.onnx_export.workflow scene-parity
python -m scripts.onnx_export.workflow verify
python -m scripts.onnx_export.workflow run
```

`python -m scripts.onnx_export` 参数（全部可省略，默认读取 `.env`）：

| 参数 | 默认值/来源 | 说明 |
|---|---|---|
| `--checkpoint` | 菜单选择的 checkpoint；直接调用时默认为模型配置 `output_dir` 中的 `best.pt` | 导出的完整 checkpoint |
| `--output-dir` | 按 checkpoint 推导 `artifacts/exports/<job>/<run>`（不读 `.env`，仅此处可显式指定） | 部署包输出目录 |
| `--deployment-profile` | `.env` 的 `ONNX_EXPORT_DEPLOYMENT_PROFILE`，否则按职业读取内置 profile | 固化部署画像 |
| `--opset` | `.env` 的 `ONNX_EXPORT_OPSET`（`18`） | ONNX opset |
| `--precision` | `.env` 的 `ONNX_EXPORT_PRECISION`（`bf16`） | 导出精度：`bf16` / `float32` / `float16` |
| `--ort-provider` | `.env` 的 `AUTOREGRESSIVE_REPLAY_ORT_PROVIDER`（`CUDAExecutionProvider`） | ORT Execution Provider |
| `--validation-devices` | `.env` 的 `ONNX_EXPORT_VALIDATION_DEVICES`（`cuda`） | 逗号分隔的 padding 验收设备 |
| `--overwrite` / `--no-overwrite` | `.env` 的 `ONNX_EXPORT_OVERWRITE` | 全部验证通过后是否原子替换已有部署包 |

`workflow` 的 `action`：

| 值 | 说明 |
|---|---|
| `all` | 环境检查、导出、两项 parity 和发布校验的完整流程 |
| `env` | 只检查 PyTorch / ONNX / ORT 环境与 BF16 支持 |
| `empty-parity` | 空 scene 128 GCD 正式 parity 门禁 |
| `scene-parity` | 真实 scene 100 执行动作正式 parity 门禁 |
| `verify` | 只校验并显示当前部署包的发布状态 |
| `run` | 用当前部署包执行一次普通 ONNX 回放 |

正式门禁参数全部来自 `.env`：

| `.env` 参数 | 默认值 | 说明 |
|---|---|---|
| `ONNX_PARITY_EMPTY_MAX_STEPS` | `544` | 空 scene 门禁步数预算，下限为 `4 × EMPTY_MAX_GCDS + 32` |
| `ONNX_PARITY_EMPTY_MAX_GCDS` | `128` | 空 scene 目标 GCD 数 |
| `ONNX_PARITY_EMPTY_REPORT` | `artifacts/onnx_parity_bf16_empty_128gcd.json` | 空 scene parity 报告 |
| `ONNX_PARITY_SCENE_MAX_STEPS` | `100` | 真实 scene 门禁统计的实际执行动作行数 |
| `ONNX_PARITY_SCENE_REPORT` | `artifacts/onnx_parity_bf16_scene_100.json` | 真实 scene parity 报告 |
| `ONNX_PARITY_TOLERANCE` | 留空 | 正式门禁只接受 manifest 精度固定阈值，留空即可 |

只有 `ffxiv_ccg.ps1 -Action export` 与 `scripts.onnx_export.workflow` 的正式门禁入口能把 parity 结果登记到部署包；
普通 `--parity-onnx-package` 调试只写外部 JSON，不会改变发布状态。BF16 导出要求显式 `CUDAExecutionProvider`
与 `--validation-devices cuda`，两项 parity 都通过后 `release_report.json` 才会晋升为 `release_validated`。

## 6. 模型自回归回放

```powershell
# PyTorch checkpoint 回放，读取 .env 的默认 checkpoint、scene 和 CUDA 配置
python -m scripts.autoregressive_replay

# ONNX Runtime 部署包回放
python -m scripts.autoregressive_replay --backend onnxruntime --onnx-package artifacts/exports/black_mage/artzip_bc --ort-provider CUDAExecutionProvider

# 调试 parity：写外部 JSON，不改变部署包发布状态
python -m scripts.autoregressive_replay --backend pytorch --scene-mode empty --parity-onnx-package artifacts/exports/black_mage/artzip_bc --parity-tolerance 1.0 --parity-output artifacts/onnx_parity_debug.json

# 历史截断消融：基准轨迹固定，只改模型可见的历史长度
python -m scripts.autoregressive_replay --max-history 240 --history-ablation 10 20 30 50
```

| 参数 | 对应 `.env` | 默认值 | 说明 |
|---|---|---|---|
| `--backend` | `AUTOREGRESSIVE_REPLAY_BACKEND` | `pytorch` | 推理后端：`pytorch` 读 checkpoint，`onnxruntime` 读部署包 |
| `--checkpoint` | 菜单选择的 checkpoint；未指定时为模型配置 `output_dir` 中的 `best.pt` | PyTorch backend 的模型文件 |
| `--onnx-package` | 按 checkpoint 路径自动推导（不读 `.env`） | ORT 部署包目录或包内 `model.onnx` |
| `--ort-provider` | `AUTOREGRESSIVE_REPLAY_ORT_PROVIDER` | `CUDAExecutionProvider` | ORT Execution Provider；不要使用允许回落的 `auto` |
| `--parity-onnx-package` | 无 | 无 | 开启 PT/ORT 双后端验收，只输出调试报告 |
| `--parity-output` | 无 | 由 `--output` 推导 `.parity.json` | parity 审计报告路径 |
| `--parity-tolerance` | 无 | 按 manifest 精度选择 | raw logits 最大绝对误差上限 |
| `--output` | `AUTOREGRESSIVE_REPLAY_OUTPUT` | `artifacts/autoregressive_rollout.md` | 回放 Markdown 输出路径 |
| `--scene-json` | `AUTOREGRESSIVE_REPLAY_SCENE_JSON` | 当前职业 raw 目录排序后的第一个 JSON | 提供完整绝对时间 scene 的 raw JSON |
| `--scene-mode` | `AUTOREGRESSIVE_REPLAY_SCENE_MODE` | `cache` | `cache` 用对应 compiled cache，`empty` 用空场景 |
| `--scene-sample` | `AUTOREGRESSIVE_REPLAY_SCENE_SAMPLE` | `0` | 从 scene 时间线第 N 个样本开始 |
| `--max-steps` | `AUTOREGRESSIVE_REPLAY_MAX_STEPS` | `100` | 最多执行的决策次数，oGCD 也占一步 |
| `--max-gcds` | `AUTOREGRESSIVE_REPLAY_MAX_GCDS` | 不限制 | 达到 N 个输出 GCD 后提前结束 |
| `--top-k` | `AUTOREGRESSIVE_REPLAY_TOP_K` | `8` | 写入 Markdown 的合法候选数量，不影响动作选择 |
| `--temperature` | `AUTOREGRESSIVE_REPLAY_TEMPERATURE` | `0` | `0` 为贪心 Top-1，大于 `0` 时按 softmax 采样 |
| `--top-p` | `AUTOREGRESSIVE_REPLAY_TOP_P` | `1.0` | 核采样阈值，范围 `(0, 1]`，仅在 `temperature > 0` 时生效 |
| `--max-history` | 无 | checkpoint/manifest 的正式容量 | 只用于显式历史截断实验 |
| `--history-ablation` | 无 | 无 | 在相同状态快照上分别只给最近 N 条历史，额外生成 `_history_N.md` |
| `--device` | `AUTOREGRESSIVE_REPLAY_DEVICE` | `cuda` | PyTorch backend 的模型与 tensor 设备 |
| `--precision` | 无 | `bf16` | PyTorch 回放权重精度 |
| `--use-kv-cache` / `--no-use-kv-cache` | `AUTOREGRESSIVE_REPLAY_USE_KV_CACHE` | PyTorch 开启、ORT 关闭 | PyTorch 模型内部 scene/history 前缀 KV cache；ORT 必须关闭 |

首步动作和预读时间由 `AUTOREGRESSIVE_REPLAY_INITIAL_ACTION` 与 `AUTOREGRESSIVE_REPLAY_INITIAL_TIME` 控制，
`AUTOREGRESSIVE_REPLAY_BASE_GCD` 控制回放使用的基础 GCD（留空时用 `config/system.yaml` 的值）。
