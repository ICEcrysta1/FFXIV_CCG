本文件记录 Rust 状态机工程 `fight-engine/`、现有 C# 工程 `Combat.Sim/FightEngine/` 与 `Combat.Sim/PythonBridge/` 的目录和运行边界。Python 适配器见[脚本](./脚本.md)，测试工程见[tests](./tests.md)，模型输入与缓存契约见[公共](./公共.md)。

## 目录与职责

### Rust 状态机

`fight-engine/` 是独立的 Cargo library crate，包名为 `fight-engine`，Rust 导入名为 `fight_engine`，使用 Rust 2024 edition。`jobs/` 下各职业分别是依赖核心的独立 crate，核心不引用它们，也不以 workspace 成员关系绑定它们。迁移按配置与状态、时间线、系统规则与职业接口、动作生命周期、职业实现、完整输出及 Python 接入逐步验证；正式 Python 调用仍使用下文的 C# 引擎。

模块采用 `名称.rs` 配合 `名称/子模块.rs` 的布局，不使用 `mod.rs`；模块文件直接实现归属逻辑，不建立空转发文件，子模块仍按职责分类；模块使用 `snake_case` 命名。系统核心与职业实现必须分离：核心不得引用或写死具体职业，职业通过接口和注册机制接入；移除职业代码后，核心仍须能独立编译并执行系统逻辑。内部时间、计算及 canonical 输出保留 `f64`，模型 tensor 数值使用 FP32／INT32；事件序号和索引保留所需位宽。行为比较严格检查离散结果、事件与动作顺序，浮点按误差验证，不要求旧舍入结果逐字节一致。

`EngineRules::from_project` 先注册启用技能的目标 DoT，再经注入的 `JobRegistry` 构造职业；核心注册表没有内置职业。`Simulator` 为每个队列独立持有时间线，排队动作冻结请求时的校验和时序；Buff 的事件顺序按授予顺序，上下文输出顺序按定义注册顺序。职业计时回调的状态、取消和排程统一转换进该时间线，不反向依赖动作载荷。历史条目与模型 frame 通过不可变 `Arc` 共享，列表写入使用写时复制隔离 fork。

宿主显式 `registry.register::<BlackMage>()` 或 `registry.register::<Machinist>()` 接入职业。职业 YAML 继续使用根目录 `config/skills/`，野火时长与量谱上限的一致性校验归机工工厂；黑魔死亡清理职业状态，机工沿用原先不清理职业状态的行为。通用资源值类型转换由核心 `ResourceValue` 实现，注册器与职业复用相同截断语义。

`serde_json` 启用 `float_roundtrip`，避免解析绝对时间戳时额外舍入改变临界事件派发；不能用放宽时间线边界代替输入精度。职业对照同时覆盖定向边界和固定输入长序列，原输出四位小数的精度差只在测试投影中处理。

Rust `SimulationEngine` 注入一份共享 `EngineRules` 与 `PolicyActionRegistry`，容量为 1–100，按 `SessionOptions` 创建队列。基础 GCD、历史上限、战斗状态、策略历史和输出缓存均属于队列；`None` 保留完整历史，`Some(0)` 关闭记录，不限制累计战斗指标。执行只取得本队列锁，响应连同时间游标原子返回。注册和关闭采用注册锁到队列锁的顺序；关闭引擎会使旧队列句柄永久失效，重置先构造再替换。

策略等待只冻结当前观测并领取共享历史序号，不提前演算下一刻；实际技能生效后领取自己的序号。完整输出按序号合并，增量输出只向量化新冻结行，并要求真实和策略历史都完整保留。输出缓存持有源 `Arc` 并按身份匹配，恢复同一序号的新历史后不会沿用旧内容；动作布局切换时重建对应 token 缓存。

`engine::replay` 的绝对序列与随机回放都在同一队列锁内执行整段操作。序列只在最后推进到已接受动作的最晚效果时刻，返回真实动作词表的 canonical；随机回放复用既有合法动作排序，SplitMix64 使用溢出回绕算术，仅选择动作时推进随机数，没有合法动作时显式推进下一内部事件。`ReplayStateCache` 从独立 fork 开始，保存完整快照并返回独立副本；缓存不拥有第二套时钟或推进规则。

基线生成与实时 C# 差分工具只用于迁移，放在不入库的 `.tmp/rust-migration/`；Rust 源码和测试目录只包含 Rust 与 JSON 数据。构建产物位于 `fight-engine/target/`，由根目录 `.gitignore` 忽略。从仓库根目录验证工程：

```bash
cargo test --offline --locked --manifest-path fight-engine/Cargo.toml
cargo fmt --manifest-path fight-engine/Cargo.toml --check
cargo clippy --offline --locked --manifest-path fight-engine/Cargo.toml --all-targets -- -D warnings
```

职业独立验证时将 `--manifest-path` 分别换成 `fight-engine/jobs/black-mage/Cargo.toml` 和 `fight-engine/jobs/machinist/Cargo.toml`。各自的 `target/` 均被忽略；删除 `jobs/` 不影响核心清单解析、构建或系统测试。

## 多队列入口与生命周期

多队列入口是 `Sessions.SimulationEngine`，Python 对应 `InProcessEngine`。一个引擎装载一份职业规则、技能表和配置，多个队列分别持有基础 GCD、战斗状态、事件时间线、策略历史及输出缓存。执行请求只获取所在队列的锁；注册锁只管理创建和释放。同队列事件必须由调用方按时间顺序提交，不同队列可以由不同 Python 线程驱动。该共享关系位于同一进程中。

```python
from scripts.common.inprocess_backend import InProcessEngine

with InProcessEngine("black_mage", capacity=16) as engine:
    # 转换与回放保留完整记录；模型读取时按 context_capacity 选择输入窗口。
    with engine.create_backend(max_history=None, actual_base_gcd=2.46) as queue:
        queue.submit_action(0.0, "fire_iii")
        observation = queue.observe_at(4.0, format="vector", next_observation_timestamp=4.0)
        counts = queue.statistics()
```

引擎容量耗尽时立即报错，由宿主负责调度待执行任务，不在引擎内部积压请求。`queue.init()` 仅重置该队列，`queue.close()` 释放队列容量，`engine.close()` 关闭全部队列；关闭的句柄永久失效。请求结果在队列锁内连同时间游标一起生成，单队列错误不关闭其他队列。职业规则装配完成后只读，运行数据必须写入传入的 `CombatState`。

## 死亡、复活与历史标记

死亡重置通过 `queue.apply_external_events([{"timestamp": t, "event_kind": "player_death"}])` 提交，成功结果的 `token` 为 `<dead/>`，普通外部事实为 `None`。系统清 MP 和公共 Buff，黑魔清职业 Buff、量谱和计时截止时刻；机工尚无职业清理规则。重置取消尚未结算的旧动作，保留 DoT、GCD、冷却、已有充能和历史，冷却与充能继续倒计时。死亡期间停止自然回蓝；`player_revived` 表示普通复活，可携带 `mp` 指定复活时 MP，未指定则由系统按 `config/system.yaml` 的 `mp_recovery.revival_ratio` 乘最大 MP 后取整，默认比例 0.2；`player_revived_lb3` 表示治疗 LB3 复活，由系统恢复完整最大 MP，不接受 `mp` 覆盖。同刻不能同时提交两种复活事实。两者均重新开启自然回蓝，不恢复死亡已清掉的状态，也不产生额外历史 token。转换器以目标复活保护出现为复活时刻；只有对应死亡区间内存在已完成的治疗 LB3，且该保护时长为 6000ms 时，才提交 LB3 复活，其余保留普通路径。缺少保护时退回死亡后首次自身动作请求；普通复活只在复活同刻有可靠 MP 记录时传入覆盖值。取消未完成请求后，最新状态的前半段保留最后已落实动作的冻结快照，后半段为当前请求状态。宿主同刻先提交外部事件，再提交新动作。转换回放中，同刻且没有复活的死亡在该刻日志旧请求全部提交后执行，场景事实仍先于请求；同刻已有复活时先执行死亡和复活。死亡标记从下一条观测起可见，末条后的死亡只重置状态。转换器已将标记保存到 PT 独立的 `history_markers` 元数据；`DeathTokenBuilder` 统一装配 token、时间和已落实历史位置，转换层补充首次可见的样本 `step`。训练按该步号读取可见标记前缀，在线回放与 GRPO 使用当前队列实际收到的死亡回执，队列初始化时清空标记。`<dead/>` 通过独立可训练的 FP32 embedding 和死亡角色进入模型，按已落实动作边界插入状态／技能对之间；不占用技能 ID，不改变状态维度或可选动作集合。历史消融快照保留当时可见的标记。

## 历史保留

`HistoryRetention` 是统一的记录保留策略：`None` 保留完整记录，整数保留最近 N 条，0 关闭记录；它不控制模拟时长和累计威力。动作与策略记录分别受上限约束，输出时再合并并保留最新 N 条。完整转换仍保存完整 history bank，既不读取模型窗口，也不改变 cache signature。完整历史占用随记录数线性增长，不能承诺无限运行时固定内存；有限窗口模式的常驻记录量有界。

## Python 桥接

桥接把观测构建和编码放在不获取 GIL 的 C# 调用中，各队列可以并行准备数据；Python 借用托管 `byte[]` 的缓冲区，通过标准库 `pickle.loads` 批量还原现有 dict/list 契约，离开 `memoryview` 后不再持有固定的托管缓冲区。编码器只产生基础值指令，唯一输入是当前程序集生成的 CLR 观测，桥接不读取外部 pickle 文件。Python 容器还原及后续 Python 逻辑仍受 GIL 约束，不能把多线程等同于整条转换流程完全并行。每次观测的可变容器保持独立，只有不可变字符串在单个包内复用。
